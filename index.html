DOGGIE · 04
Independent Project · Industrial Design · 2025

DOGGIE 多功能宠物牵引绳

用户调研 独立设计 多轮纸模验证 完整交付

宠物「出门—活动—回家」的连续过程里，牵引、玩具携带、垃圾袋收纳、入户前脚底清洁这些高频需求 分散在不同用品和步骤里——把同一次外出链路中的高频需求，整合进一个随身牵引产品。

01 · CONTEXT

为什么做

核心不是「想做一个多功能牵引绳」。真正的问题是需求分散：同一个用户、同一次外出， 要换好几样东西、走好几道步骤。

02 · RESEARCH

用户 / 竞品研究

通过用户调研与竞品调研梳理需求分散点，确定以「一次完整外出」作为整合单位。

03 · STRATEGY

设计策略

不做「功能越多越好」，而是按外出链路的时间顺序，把可用性最高的几项能力收进一个随身产品。

04 · SOLUTION

方案与结构

  • 环形握持与牵引控制
  • 透明玩具球仓
  • 可拆卸脚底清洁刷
  • 把手内垃圾袋收纳
  • 概念结构与分件
05 · PROTOTYPE

纸模验证

多轮纸质模型握持测试。

纸模原始照片已遗失；如需出示，只放明确标注为「方法复原示意」的图， 不作为真实留档照片。

06 · ITERATION

改了什么

测试结果真实改变了设计：按实际持握结果调整了把手宽度、把手长度、整体比例。

07 · RESULT

最终成果

Rhino 模型与分件 · KeyShot 渲染与多视图 · 使用场景 · Logo · 包装 · 作品集呈现。

目录含 19 个 Rhino、23 个 KeyShot 工程与数百张过程 / 结果图。

不收起也可以继续往下滚

LUMORA · 05
Independent Project · Industrial Design · 2025

Lumora 光健康伴护仪

适老设计空间整合 尺寸规划多状态设计

面向老年疗养照明场景，把照明、收纳、移动与空间效率组织进一套简洁的产品系统。

01 · CONTEXT

为什么做

适老化灯具的实际使用问题。

02 · PROBLEM

现有疗养灯的问题

疗养 / 适老类灯具普遍太功能化、太「医疗器械感」，造型不好看， 难以融入家居环境。

依据：产品调研与竞品调研。

03 · STRATEGY

设计策略

用结构的改变换使用体验的改善：折叠换取空间、脚轮换取移动、 简洁造型换取环境融入。

04 · FOLD

折叠

折叠结构 → 节省收纳空间。

05 · MOVE

移动

底部脚轮 → 方便老人自行移动产品。

06 · DIMENSIONS

尺寸与部件

可调灯臂 · 物理控制区 · 抽屉收纳 · 挡板（遮蔽内部部件、保持外观完整）· 移动结构。

  • 350 × 350 mm主体
  • 572 mm收纳总高
  • 1280 mm展开最高
  • 270 × 110 mm抽屉开口

概念尺寸（Rhino 模型实测）。

07 · STATES

展开 / 收纳

交互：收纳态 ↔ 使用态切换（状态切换即可，不做复杂 3D 动画）。

边界：上述尺寸为数字模型概念尺寸，非工程测试值；不做功效宣称。

08 · RESULT

最终成果

外观方案 · 完整多视图 · 概念结构与部件示意 · 收纳 / 展开状态尺寸图 · 四类场景图（客厅休息 / 床边 / 桌面阅读 / 座椅阅读）· 完整展板。

DESKTOP ROBOT · 08
RUNNING PROTOTYPE · 已运行原型
AI Product · Self-initiated · 2026

桌面陪伴型机器人

AI 产品能力模块化 ESP32 实机语音闭环

面向长期在桌面学习、工作与创作的青年用户，构建「可成长」的实体 AI 机器人系统， 把语音交互、私人后台、ESP32、状态反馈与有限外部设备能力组织成可运行的实机原型。

01 · USERS

用户与场景

核心用户：长期使用个人桌面学习、工作或创作的青年——大学生、初入职场者、 程序员、设计师、内容创作者。

扩展用户：居家办公者、自由职业者、智能硬件 / 桌面 DIY 爱好者。

明确不属于当前主要目标：儿童照护、老年人看护、医疗陪护。

场景是个人桌面。出发点是这些能力当前分散在手机、电脑、音箱和不同软件里。

02 · CONCEPT

产品概念

「陪伴」不是机器人一直聊天或卖萌，而是让语音、屏幕表情、身体动作、设备执行反馈 彼此配合，让用户清楚知道机器人当前是：倾听 · 思考 · 确认 · 执行 · 成功 · 失败 / 出错。

03 · MODULARITY

可成长 / 能力模块化

形态不必固定，能力可以按需要组合。稳定交互核心 + 有限范围内允许： 更换装饰外壳 · 增加角色化配件 · 增加动作能力 · 连接指定外部设备。

边界：不宣称「万物皆可连接」，不做通用协议， 只强调明确接口 + 有限设备范围验证。

04 · FORM

交互状态与形态

不追求完整人形——桌面空间有限、复杂人形抬高制作成本。用头身关系、屏幕眼睛 / 表情、 少量关节、动作节奏建立角色感。

原则：状态表达清楚 > 复杂人形动作。

05 · ARCHITECTURE

系统架构

四层：机器人本体 / 私人后台 / 控制层 / 执行模块。

私人后台承担：硬件通信、状态同步、ASR、LLM、TTS、模型接入、动作与设备控制指令、 执行结果回传。

A基础语音交互链路 B系统状态 / 语音 → 机器人动作链路 C外部设备控制链路

DESIGN DNA · 09
Self-initiated · AI Workflow · Web MVP · 2026

DesignDNA 工业设计协同工作台

问题抽象产品规则 AI 工作流Web MVP

将当前产品的关键设计特征提取为可编辑 Product DNA，通过 Fixed / Controlled / Free 控制 AI 的探索范围。

打开界面走查 ↗ 可点：四步工作流逐屏走查

01 · PROBLEM

问题

AI 辅助改款的两难：放得太开 → 不像原产品；限得太死 → 没有探索价值。

根因是「哪些特征决定识别性、哪些可以动」没有被显式定义。

02 · PRODUCT DNA

动态 Product DNA 提取

工作台先读基准图、识别产品类型，再把产品拆成 6 个可指认的设计维度， 并在每个维度下写出该产品自己的特征描述与细节。

口径：槽位固定、内容自适应。这 6 个维度是当前实现的 维度骨架，不是跨品类通用模型；每个产品得到的是完全不同的特征项。

跨品类实测对照（工作台真实输出）
维度骨架便携式双单元音响手提式烧水壶
主体轮廓竖直矩形箱体 + 顶部一体式门形提手圆筒壶身 + 收窄锥台肩 + 圆形壶盖 + 拱形提手
核心比例箱体高宽比约 1.5:1；单元直径占正面宽 22–25%壶身宽约总高 80%；提手高约总高 35%
交互布局顶部窄横向控制带（input / play / volume / tape）提手 + 壶盖中央旋钮；无电子界面
倒角与边界直线边界 + 小幅圆角；扬声器多层圆环过渡大圆角与连续弧面；壶盖多道水平环形边界
表面层级红色主箱体 / 深色控制带 / 黑色声学组件同心分层镜面金属壶身 / 深色锥台肩 / 黑色提手三分区
标志特征正面双圆形扬声器 + 左侧外露竖向结构件黑色倒 U 形提手 + 三段式色材组合 + 左侧上扬壶嘴

两个案例均无可见 Logo / 品牌文字，模型自述「不可辨识可确认的 Logo、品牌文字或型号标记」。

03 · THREE STATES

Fixed / Controlled / Free

把每条提取出的特征映射到三态，并写明原因与重要度（1–5）。三态直接编译进生成 prompt：

状态中文含义进入 prompt
fixed固定绝对不能变，评审时逐条核对MUST KEEP
controlled受控可以改，但要守住核心属性MAY REFINE
free自由放开探索FREE TO EXPLORE
实测（两个跨品类案例都跑过完整链路）
案例约束条数三态分布
便携式双单元音响14 条4 固定 / 7 受控 / 3 自由
手提式烧水壶15 条4 固定 / 8 受控 / 3 自由

每条约束含「特征名称 · 所属维度 · 原因说明 · 重要度（1–5）· 英文指令」， 并可手动钉住（钉住的条目重新生成时不会被覆盖）。两个产品的三态比例接近， 但内容完全不同——音响钉的是「双扬声器开孔、顶部控制区、可携提承重」， 水壶钉的是「宽矮比例、圆筒加锥台轮廓、壶嘴上扬、提手与壶盖关系」。

工作台自己的定位：「它不懂你的模具和供应链，最终拍板的是你」。 一条 Fixed 都没有时会警告「生成时没有任何硬约束，结果很可能面目全非」。

04 · STRATEGY

探索策略

三档策略按激进程度递增，每一档给出具体的设计语言命名（工作台真实输出）：

  • 便携式双单元音响：运动装备分层精修 + 精密黑红 CMF ／ 圆角嵌套箱体 + 运动护框融合 ／ 智能表盘护甲 + 运动鞋底式一体骨架
  • 手提式烧水壶：复古轮廓精修与连续环带强化 ／ 肩部张力重构与拱顶提手对比 ／ 环形阶梯体块与悬浮拱架探索

另有四种发散方式（造型 / 思维 / 色彩材料 / 造型融合）与九宫格批量发散 （造型九宫格、CMF 九宫格，3×3＝9 个完整方向）。

05 · REVIEW

评审 / 矩阵比较

评审维度：约束符合度 · 可制造性 · 保持度 · 创新度 · 市场契合； 结论为 采纳 / 继续迭代 / 否决，并逐条给出符合度与文字证据。

实测：约束符合度 96–100%，逐条 pass。

硬规则：一旦检测到 Fixed 约束被破坏，直接判定「这一版无论多好看都不能直接采纳 —— 它改了不该改的地方」。

另有变体树（父子迭代）、原图对照与对比矩阵。

06 · WEB MVP

Web MVP

已做成可运行的本地 Web 测试原型：左栏为项目 / 简报 / 基准图 / 参考图， 中间画布支持变体树 · 单图 · 原图对照 · 对比矩阵，右栏即四步工作流 （理解 → 锁定 → 探索 → 评审）。

本人负责需求定义、规则组织、交互调整与真实产品图验证；实现借助 AI 完成。

口径：不表述为独立软件工程能力。

07 · VALIDATION

验证

用真实产品图验证，并根据失败案例、易用性问题持续迭代。

可补强：测试产品数量；「无约束 vs DesignDNA 约束」的 Before / After 对照。
